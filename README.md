# VGXNESS

**Current:** This repository delivers a Go 1.26 control-plane foundation with the `vgxness` executable, a versioned self-installer with atomic activation and rollback, Chronicle events/snapshots/recovery, an owned unified SQLite/FTS5 memory store partitioned by project, Registry/Gatekeeper policy, provider-neutral bounded coordination, exact prompt composition, and a hardened OpenCode runtime adapter with a persistent Node/Bun-compatible `vgxness_*` bridge. CI validates tests, race detection, coverage, vet, formatting, module integrity, and builds with Go 1.26.3.

The read-only `status` and `doctor` inspection commands report resolved storage paths, the SQLite migration version, and an active Chronicle run when present. `doctor --deep` also verifies current-run, orchestration, native-ticket, and native-lease state; `orchestrate list` exposes the durable orchestration inventory. `maintenance prune` is a dry run unless `--apply` is explicit, only considers verified terminal documents older than the requested retention, preserves referenced or leased tickets, and never removes lock files. Inspection does not create a missing database or current-run file. The CLI can install, inspect, update, and roll back its permanent launcher, then use an explanatory, confirmation-gated wizard to install and verify `vgxness-manager`, four permission-scoped native OpenCode subagents, and the managed plugin bridge. `vgxness_orchestrate` creates a native Navigator child, validates its proposed tasks, persists a deterministic plan, and returns each legal wave with one exact built-in OpenCode Task arguments object per approved task. A normal one-shot `vgxness_dispatch` skips Navigator but uses the same native Task contract and durable join, so its single child session is also visible and navigable in OpenCode. OpenCode therefore renders one live execution row per native subagent, including several parallel rows, while each child must claim and complete its VGXNESS ticket before it can discover paths, read evidence, query the optional CodeGraph structural broker, edit through the isolated worktree broker, or publish a result. At most four independent reads overlap; mutation remains exclusive. `write-files` starts only from a clean committed Git root, writes at most 32 digest-guarded UTF-8 replacements or creations in a detached sibling worktree, rejects direct or sensitive changes, and publishes a durable base/path/content manifest without silently merging the result. The local `vgxness edit inspect|review|approve|integrate|retire|discard` lifecycle issues a Delivery Authority receipt over the isolated worktree, requires its exact active identity for approval, revalidates it before integration, applies only into the unchanged clean source checkout, supports crash-safe replay, and removes the worktree only through an explicit verified disposition. Dependent waves receive only bounded validated evidence and close through one durable join. A per-task claim capability can reconstruct an admitted Task ticket after a lost plugin response without exposing prepared prompts through ordinary status or the public owner identity. Owner/epoch takeover, `status`, `resume`, `cancel`, and `explain` remain available without nested workers. Explicit dispatch continuity remains a backward-compatible direct-session path; normal multi-phase manager routing uses visible orchestration. `vgxness delivery issue|status|validate|invalidate` persists content-bound review receipts and reuses them across post-apply, pre-commit, pre-push, and pre-PR validation without reopening review. Full SDD artifacts, automatic Git/branch-protection wiring, richer review automation, the keyboard TUI, and additional runtime adapters remain planned.

VGXNESS is planned as a local-first agent orchestration system that keeps human control, operational state, permissions, and validation explicit. The canonical product purpose, vocabulary, boundaries, and roadmap live in the [VGXNESS Product Blueprint](docs/product-blueprint.md).

## Direction

VGXNESS coordinates bounded capabilities through a Go control plane, Chronicle operational truth, an owned SQLite/FTS5 semantic `MemoryStore`, and runtime-neutral adapters. OpenCode is the first implemented runtime adapter, persistent manager surface, bounded bridge, and guided CLI setup; a richer keyboard TUI remains planned. CodeGraph is implemented as an optional ticket-bound structural-intelligence broker for native explorer sessions; OpenPencil remains a preferred optional design adapter, and Engram remains an optional compatibility/import/reference adapter. All are subject to capability, permission, provenance, and policy checks.

By default, semantic memory for every workspace lives in one user database at `~/.vgxness/memory.db`; a canonical workspace registry keeps same-named projects distinct while preserving an existing legacy project identity on first binding. Project scope, topic keys, sessions, and references remain isolated inside the schema. Every bounded dispatch/orchestration task retrieves up to three relevant observations, hydrates their bounded content into the child execution packet, and writes one idempotent result observation that references the evidence it used. Chronicle, native tickets, delivery receipts, and other operational files stay under `~/.vgxness/projects/<project-id>/`. On first memory access after upgrading, an existing project-level `memory.db` is imported transactionally and idempotently, while the old file is retained as an inactive recovery backup. Explicit `--storage-root` and `--project-local` modes remain isolated overrides.

**Implemented/Planned:** Navigator now plans and coordinates bounded native OpenCode read, isolated edit, and review tasks. The edit broker delivers an explicit worktree artifact; local operators can inspect, content-bind approval, integrate, retire, or discard it, while automatic review and merge remain intentionally absent. Scout, Blueprint, Forge, Sentinel, optional Challenger, and their complete SDD artifact workflows remain product capabilities under construction. Registry, Chronicle, and Gatekeeper are deterministic services; explore, design, apply, and verify are operating modes rather than a competing capability taxonomy.

**Non-goal:** VGXNESS will not copy third-party code, prompts, schemas, names, skills, or exact workflows, and it will not permit silent destructive autonomy or hide operational truth behind a CLI.
